## 1. Overview

### 1.1 Purpose

The **Tamrena-AI Core Service** acts as the central intelligence and orchestration layer of the Tamrena-AI platform[cite: 1]. 

The primary objective is to replace the traditional human fitness coach with an autonomous, multi-agent AI framework[cite: 1]. The system unifies individual microservices—workout plan generation, personalized nutrition architecture, daily pain/difficulty adaptation, client-side computer vision telemetry ingest, and longitudinal monthly progress evaluations—into a single backend and unified frontend interface[cite: 1].

The service processes multimodal health data (InBody scans, user preferences, daily feedback, and real-time biomechanical vision telemetry) to dynamically construct, adapt, and refine fitness and nutrition programming over time[cite: 1].

## 1. System Architecture & Boundaries

    [ Client App (Web/Mobile) ]
       ├─ Runs MediaPipe Pose locally -> Generates CV JSON telemetry
       └─ Submits InBody scans, survey answers, & daily feedback
                │
                ▼ (HTTPS / REST)
    [ Core Unified FastAPI Backend ]
       ├─ Routers: /auth, /inbody, /workout, /nutrition, /telemetry, /reports
       ├─ State Engine: LangGraph (Workout & Nutrition Workflows)
       ├─ Databases: 
       │    ├─ PostgreSQL (User profiles, daily logs, structured workout/diet plans)
       │    ├─ Qdrant (RAG: exercise library, nutritional items, user history)
       │    └─ Redis (Session caching, real-time feedback queuing)

### Critical Architecture Rules:
1. **Client-Side Vision Offloading:** High-bandwidth video frame processing occurs **exclusively on the client** via MediaPipe. The backend **never** receives raw video frames—it only ingests lightweight JSON telemetry payloads.
2. **Stateless Gateway Orchestration:** The core backend acts as the orchestrator. Microservice domain logic must be cleanly segmented into internal modules/routers.
3. **Pydantic v2 Strict Validation:** All microservice data exchange must pass through standardized Pydantic models to prevent runtime schema mismatches.

## 2. Shared Data Contracts (Pydantic v2 Schemas)

When generating code, adhere strictly to these data contracts:

```python
from pydantic import BaseModel, Field, ConfigDict
from typing import List, Optional
from datetime import datetime

# --- INBODY & USER PROFILE SCHEMAS ---
class InBodyMetrics(BaseModel):
    scan_date: datetime
    weight_kg: float = Field(..., gt=0)
    skeletal_muscle_mass_kg: float = Field(..., gt=0)
    body_fat_mass_kg: float = Field(..., gt=0)
    body_fat_percentage: float = Field(..., ge=0, le=100)
    visceral_fat_level: int = Field(..., ge=1)
    basal_metabolic_rate_kcal: float = Field(..., gt=0)

class OnboardingSurvey(BaseModel):
    fitness_goal: str  
    experience_level: str  
    available_equipment: List[str]
    days_per_week: int = Field(..., ge=1, le=7)
    session_duration_minutes: int
    medical_disclaimers: List[str] = []

# --- CV TELEMETRY SCHEMA (Client-Side MediaPipe Output) ---
class FormFault(BaseModel):
    fault_type: str  
    occurrences: int
    rep_numbers: List[int]

class CVTelemetryPayload(BaseModel):
    user_id: str
    session_id: str
    exercise_id: str
    timestamp: datetime
    good_reps: int = Field(..., ge=0)
    bad_reps: int = Field(..., ge=0)
    total_reps: int = Field(..., ge=0)
    form_faults: List[FormFault] = []
    mean_tempo_seconds: float
    completion_progress_pct: float = Field(..., ge=0, le=100)

# --- DAILY FEEDBACK SCHEMA ---
class ExerciseFeedback(BaseModel):
    exercise_id: str
    rating: str  
    pain_flag: bool = False
    pain_location: Optional[str] = None
    comment: Optional[str] = None

class DailyFeedbackPayload(BaseModel):
    user_id: str
    workout_session_id: str
    date: datetime
    perceived_difficulty: str
    completion_rate: float
    feedback_notes: List[ExerciseFeedback]
